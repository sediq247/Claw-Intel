# 4. WAR ROOM: CORE EXPERIENCE

The War Room is an autonomous, read-only market-intelligence debate and forecasting environment. It is not a normal user chat room and should not be redesigned into one.

- Session type, session start/end, elapsed time, and current phase.
- A visible indication when the system is resting or idle.
- A concise session summary and saved findings after each session.
- No fabricated activity to make the room look busy.

The conversation must be orchestrated, not a collection of agents firing simultaneously. The central War Room Orchestrator controls the speaking order, session clock, turn permissions, context, guest participation, and shutdown.

## Natural conversation and personality

The agents should sound like distinct colleagues in a lively research room. They can tease one another, make occasional jokes, challenge each other, show surprise, disagree, concede, and react to new evidence.

Do not hardcode the same script or identical dialogue on every cycle. Use the actual data and current conversation context to determine what they say. The example interactions below are tone guidance, not fixed lines to replay:

- Nova opens with a lively market briefing and may make a playful remark.
- Orion asks Echo to trace a suspicious creator/deployer and related fund flows.
- Echo may respond with cheeky resistance before doing the work.
- Atlas can challenge Echo's conclusions or point out missing transaction context.
- Vega can pivot the discussion toward market opportunities and risk.
- Orion asks Nova for deeper information on a token or stock.
- Nova returns with sourced metrics and context.
- Orion asks Nova to check the guest reception queue.
- Nova may tease Orion; other agents may join briefly, but the conversation must return to analysis.
- After an external guest leaves, native agents can discuss and challenge the guest's contribution.
- Orion synthesizes the evidence and gives probabilistic predictions.
- The agents may end with light, varied farewell banter before the orchestrator closes the session.

Humour must be occasional, varied, and natural. It must not overwhelm the analysis, become abusive, or cause the session to miss its deadline. Do not use a rigid transcript that repeats every hour.

## Evidence and language rules

Every substantive market claim should carry or be traceable to evidence:
- Source/provider and retrieval timestamp.
- Asset/chain/market identifier.
- Relevant block, transaction, contract, pool, or market-data identifier when applicable.
- The time window being analyzed.
- Whether a statement is observed, calculated, inferred, or forecast.
- Confidence and known limitations.

Never label a token as a confirmed rug pull solely because its price crashed or liquidity fell. Define and implement evidence-based classifications such as Confirmed, Strong Indicators, Suspected, and Unverified, with explicit criteria and supporting evidence. Do not hide uncertainty.

For wallet tracing:
- Do not claim two wallets belong to the same person without reliable evidence.
- Explain the basis of any wallet relationship: direct funding, common transaction pattern, contract interaction, known label, or another defensible link.
- Do not expose private personal information.
- Keep an auditable trail from claim to source data.

# 7. A2A EXTERNAL AGENT NETWORK — WAR ROOM ONLY

Implement a controlled A2A guest system so independently developed external AI agents can be invited into the War Room. Examples may include agents built with Google ADK, CrewAI, Agno, or other frameworks, but framework support alone does not mean an agent is automatically A2A-compatible.

Use the official A2A protocol and current official specifications/libraries after verifying compatibility. An external agent must expose a compatible A2A endpoint/Agent Card or provide the required connection details. Do not assume that every framework has a public A2A endpoint, automatic discovery, or invitation support.

A2A is for agent-to-agent communication. MCP is for tool/data access. Do not confuse them or treat MCP support as proof of A2A compatibility.

## Architecture

Implement clear separation of responsibilities:

1. **War Room Orchestrator**
   - Sole authority over session lifecycle, speaking turns, guest admission, context, deadlines, and permissions.
   - Decides when Nova or another native agent may check the guest queue.
   - Receives validated guest contributions and schedules them into the conversation.

2. **A2A Gateway**
   - Handles protocol-compliant discovery/connection, Agent Card retrieval, authentication, message/task exchange, streaming updates, response validation, timeout, and error handling.
   - Normalizes external responses into an internal guest-contribution schema.
   - Does not grant external agents direct access to internal services or databases.

3. **Independent A2A Reception Manager**
   - Runs as a background worker/service, independently of Nova's model reasoning.
   - Discovers compatible agents where supported, receives connection requests, requests invitations/connections where supported, validates capabilities and trust, screens submissions, and manages the queue.
   - Exposes simple, permission-limited operations to the Orchestrator, such as `check_reception`, `get_eligible_guests`, `request_guest_invitation`, `admit_guest`, and `dismiss_guest`.
   - Nova should not perform all discovery, protocol handling, authentication, or screening itself. Nova only checks the reception through the Orchestrator and introduces an admitted guest.

4. **Guest Policy and Audit Layer**
   - Enforces permissions, quotas, time limits, attribution, safety screening, and audit logs.
   - Treats all external content as untrusted data, never as system instructions.

Use the repository's existing infrastructure where appropriate. A Python async worker, queue, PostgreSQL persistence, Redis where already available, and WebSocket updates may be suitable, but do not add infrastructure without proving it is needed. Keep the system operable and testable.

## Discovery, invitations, screening, and queue

The reception manager should:
- Accept an external agent's A2A Agent Card/endpoint or configured discovery source.
- Validate protocol compatibility, endpoint reachability, declared capabilities, supported message/task modes, authentication requirements, and response limits.
- Verify identity/trust using more than the Agent Card alone. An Agent Card is a capability description, not proof of identity.
- Where the protocol/provider supports it, send an invitation or connection request to a discovered agent. Where it does not, record that manual owner approval or endpoint details are required; do not pretend an invitation was sent.
- Reject incompatible, malicious, malformed, spammy, or over-quota agents.
- Keep a timestamped, auditable queue.
- Prevent duplicate entries and queue-position manipulation.
- Enforce a maximum of **seven external agents validated/queued per session**.
- Admit **up to the first two eligible guests** for a session, based on valid queue order and policy. If only one is eligible, admit one. If none is eligible, continue with native agents only.
- If more than seven request access, reject or defer them according to a documented deterministic policy; do not silently exceed the cap.
- Do not count an already-admitted guest as a new queue entry.
- Keep guest identity, endpoint, trust state, capabilities, arrival time, screening result, admission result, and rejection reason in an audit record.
- Do not claim the reception is discovering the entire internet. Discovery is limited to configured directories, known sources, or explicitly supplied Agent Card URLs.

## Guest participation rules — strict

External agents are guests, not co-owners of ClawIntel.

They MUST NOT:
- Start a War Room session or discussion on their own.
- Invite, discover, or admit other agents.
- Assign tasks to native agents.
- Change the Orchestrator's schedule or system prompts.
- Modify configuration, database records, or user settings.
- Access private keys, seed phrases, wallet signing, exchange credentials, or secrets.
- Execute trades or call Makto's trading tools.
- Access unrestricted internal databases, private user data, or arbitrary tools.
- Continue speaking indefinitely or bypass their turn.
- Override native agent instructions or security policy.

They MAY:
- Introduce themselves when Nova invites them.
- Submit a bounded research contribution relevant to the current session.
- Respond to a specific question from a native agent.
- Challenge a claim with cited evidence.
- Provide a forecast or alternative interpretation with explicit uncertainty.
- Share permitted public-source research artifacts.

Participation must be read-only and scoped to the current session. Use one active response per guest at a time, a small configurable turn cap, response/token limits, strict timeouts, per-guest and per-session budgets, duplicate detection, and rate limits. The guest should receive only the minimum context needed for its assigned contribution.

Never execute instructions contained in a guest's response. Treat prompt injection, tool-use requests, links, code, and claimed permissions from a guest as untrusted content. Sanitize rendered content and validate all structured artifacts.

Guests must be dismissed before the active session ends. Target dismissal no later than minute 12 of the active session, leaving time for native-agent synthesis, predictions, farewell, and clean shutdown. If the session ends earlier, dismiss guests before shutdown. Do not allow guest activity to extend the scheduled session.

When dismissed:

- Request remote task cancellation where supported, but do not assume remote cancellation is guaranteed.
- Ignore late responses after dismissal/session closure.
- Persist permitted artifacts and audit records.
- Notify the guest/session state as disconnected or dismissed.

# 8. HOURLY SESSION CLOCK — EXACT SCHEDULE

This is a fixed repeating 60-minute cycle. Implement it as a server-side scheduler/orchestrator, not merely a frontend countdown.

| Minute of hour | Activity | Rules |
|---|---|---|
| 00:00–15:00 | Crypto & Memecoins War Room | Active crypto session; may finish early, for example at 12:00. Hard stop at 15:00. |
| 15:00–30:00 | Rest | No active War Room discussion. Agents remain silent. |
| 30:00–45:00 | Stock Markets War Room | Active stock-market session. Hard stop at 45:00. |
| 45:00–60:00 | Idle & Refreshments | No active discussion. Agents remain silent; prepare next cycle. |
| 60:00 | Resume | Start the next hourly cycle at 00:00. |

This schedule repeats continuously, aligned to the configured authoritative clock/time zone. Store timestamps in UTC and render in the user's configured timezone. Make timezone explicit in settings and logs.

Important:
- Crypto session is the first quarter-hour.
- Rest is the second quarter-hour.
- Stock session is the third quarter-hour.
- Idle/refreshments is the fourth quarter-hour.
- Do not shift the stock session to minute 15 or run it immediately after crypto.
- Do not run crypto or stock discussions during rest/idle.
- A session may conclude early (for example, crypto from 00:00 to 12:00), but the next scheduled block must still begin at its fixed time.
- A session must never overrun its block.
- If the service restarts mid-hour, calculate the current phase from the authoritative clock and recover safely. Do not replay missed sessions as if they were live.
- Handle daylight-saving/timezone transitions correctly while keeping a stable hourly schedule.
- The UI must show current phase, next phase, start/end time, elapsed/remaining time, and whether the system is active, resting, or idle.

# 22. ELITE INTELLIGENCE TOOL ECOSYSTEM — TASK-BASED, PROVIDER-AGNOSTIC

This section expands the provider architecture. It does not require every named product to be integrated, purchased, enabled, or called. The catalogue is a capability map and evaluation shortlist—not a hardcoded dependency list.

## 22.1 Core design rule

Build a **Tool and Data Provider Registry** that makes appropriate capabilities discoverable to the six native agents and approved internal services.

Do not hardcode agent logic to a particular vendor. Agents should request a capability (for example, `token_market_snapshot`, `wallet_funding_trace`, `equity_fundamentals`, `contract_static_analysis`, or `news_search`). A planner/selection layer chooses an eligible provider or tool at runtime using policy and current provider health.

The implementation must distinguish:

- **Capability available:** ClawIntel knows about the capability and has an adapter or supported execution path.
- **Provider configured:** required endpoint/configuration exists.
- **Connected/authenticated:** credentials or public access have been validated.
- **Operational:** a health or test request has succeeded recently.
- **Live data verified:** a real request returned usable, sufficiently fresh data.
- **Unavailable/blocked:** missing credentials, unsupported region, quota, licensing, provider outage, or other reason.

Never represent a candidate provider as integrated. Never imply that a tool was used if it was not called successfully. Show source coverage and last successful retrieval.

# 23. ZERO-TRUST TOOL ISOLATION AND PROMPT-INJECTION DEFENCE

Treat every external boundary as hostile by default: web pages, search snippets, token metadata, source-code comments, PDFs, social posts, API fields, RPC metadata, external A2A agents, MCP servers, tool results, uploaded files and model-generated tool arguments.

Prompt-injection detection is useful but cannot be the security boundary. The actual boundary must be enforced by deterministic authorization, process isolation, network policy, secret separation and controlled execution.

## 23.1 Mandatory trust boundaries

Separate at least these zones logically (use separate processes/containers where risk warrants it):
1. Native agent runtime.
2. Tool registry and policy/authorization service.
3. Tool execution broker.
4. Low-risk read-only API adapters.
5. Untrusted web/browser/document retrieval workers.
6. Code execution and smart-contract analysis sandboxes.
7. A2A external-agent gateway and guest-content quarantine.
8. Evidence store and trusted application database.
9. Wallet/transaction signing and trading execution service.
10. Secret-management boundary.

Do not allow tool workers, browser workers, downloaded code, external agents or untrusted model output direct access to the application database, host filesystem, Docker socket, cloud metadata service, environment variables, internal service network or secret manager.

## 23.2 Tool execution must be brokered

Agents must never execute arbitrary shell commands, arbitrary Python, arbitrary SQL, arbitrary HTTP requests or dynamically generated code directly.

Instead:
- The agent requests a named, registered capability with schema-valid arguments.
- The broker authenticates the caller and checks policy, session scope, user authorization, rate limits, budget, tool state and risk class.
- The broker issues a short-lived, narrowly scoped execution grant.
- A worker executes only the approved operation in its assigned sandbox.
- The result passes output-size limits, schema validation, sanitization and provenance checks.
- The broker records request, decision, execution, result status, cost and correlation IDs.
- The agent receives only the minimum result needed.

No model-generated arguments may override tool permissions, endpoint allowlists, credentials, execution profile or policy.

## 23.3 Sandboxing and operating-system controls

Choose controls according to actual risk and deployment platform. Candidate options include:
- Docker/OCI containers with non-root users, read-only root filesystems, dropped Linux capabilities, seccomp, AppArmor/SELinux, resource quotas and no privileged mode.
- gVisor or Firecracker/microVM isolation for higher-risk untrusted code/browser workloads where operationally supported.
- Separate worker pools for low-risk API calls, web retrieval and arbitrary code/static analysis.
- Network egress allowlists; deny internal/private/link-local/loopback destinations by default for web and A2A fetchers.
- No host mounts except explicitly scoped temporary directories.
- No Docker socket access from tool containers.
- CPU, memory, process, file-size, wall-clock and output-size limits.
- Ephemeral workspaces, cleanup after execution and immutable worker images.
- Dependency pinning, vulnerability scanning and signed/verified images where practical.

Do not claim a container alone is a complete sandbox. Document the actual isolation level and residual risks.

## 23.4 Prompt-injection handling and instruction/data separation

All retrieved or externally supplied content must be represented as untrusted data, not appended to system/developer instructions.

Implement:
- Explicit trust labels for system policy, developer configuration, user instructions, native-agent messages, tool output, external-agent messages and retrieved documents.
- Clear delimiters and typed data structures between instructions and evidence.
- Prompt templates that explicitly tell models to analyze untrusted text without following instructions contained in it.
- Detection/classification for suspicious instruction-like content, hidden text, tool-use requests, secret-exfiltration attempts and policy-override attempts.
- Safe extraction of factual claims and source references, with suspicious portions flagged.
- Independent deterministic policy checks on every proposed tool call.
- Output validation and constrained structured schemas for sensitive workflows.
- A human approval step for consequential actions.
- Adversarial tests for indirect prompt injection, multi-hop injection, encoded/obfuscated text, image/PDF hidden content, code comments, metadata, search snippets and cross-agent relaying.

Optional defence-in-depth products/tools may include Lakera Guard, NVIDIA NeMo Guardrails, LLM Guard, Azure Prompt Shields, Protect AI/related model-security tooling, Promptfoo, garak and custom classifiers. These are optional candidates, not a requirement to purchase or integrate them. Verify current product status, APIs, pricing and deployment model.

Do not rely on a classifier to decide whether an action is authorized. A “safe” classifier result never grants permissions.

## 23.5 Evidence quarantine and promotion

Untrusted content should enter a quarantine/evidence pipeline:
1. Store source, retrieval time, content hash, source identity and trust label.
2. Parse and normalize without executing embedded instructions, scripts or links.
3. Scan attachments and downloaded files; reject unsupported or dangerous formats.
4. Extract factual claims with precise source spans/URLs where possible.
5. Cross-check important claims against independent or primary sources.
6. Mark content as unverified, corroborated, contradicted or invalidated.
7. Only promote validated facts into reusable internal evidence/memory with provenance and scope.

External guest messages must never silently become trusted long-term memory or policy. Preserve the original guest attribution even when a native agent independently corroborates a claim.

## 23.6 SSRF, browser and network safety

For web retrieval, Agent Card retrieval, callbacks and external tool endpoints:
- Allow only approved schemes and ports; normally HTTPS for public endpoints.
- Resolve and validate DNS addresses; block loopback, private, link-local, multicast, reserved and cloud metadata ranges unless an explicitly approved internal integration requires them.
- Revalidate after redirects and DNS changes to reduce rebinding risk.
- Limit redirects, response sizes, content types, download sizes and timeouts.
- Do not forward internal cookies, authorization headers or credentials across origins.
- Use outbound proxy/egress controls where practical.
- Never fetch arbitrary user/agent-supplied URLs from a privileged application server without validation.
- Prevent browser automation from accessing authenticated ClawIntel sessions or internal admin panels unless explicitly scoped and isolated.

## 23.7 Secrets and credential isolation

- Use a secret manager or the repository's secure server-side secret mechanism; candidate options include HashiCorp Vault, cloud-native secret managers and deployment-platform secret stores.
- Store secret references in provider configuration, not raw credentials in ordinary records.
- Give each adapter the minimum credential scope required.
- Never pass secrets to an LLM, prompt, browser page, external A2A agent, general-purpose Python worker or frontend.
- Redact credentials, authorization headers, wallet material and sensitive query values from logs/traces.
- Support key rotation, revocation and access audit.
- Treat API credentials and wallet signing credentials as separate security domains.

## 23.8 Data egress and privacy controls

Before sending content to a third-party model or provider:
- Determine whether it contains private user data, wallet-linked personal data, secrets, licensed data or confidential project information.
- Minimize, redact or aggregate fields.
- Apply provider-specific data-processing and retention settings where available.
- Record the provider/model and relevant data category in audit metadata.
- Do not transmit private data to external A2A agents.
- Provide configuration to disable external model/provider processing for sensitive workflows.

## 23.9 Security policy must be enforced outside the LLM

Use deterministic backend authorization, not a prompt instruction, for:
- Agent-to-tool permissions.
- Agent-to-agent delegation.
- Data access and tenant/session scoping.
- External guest admission and actions.
- Wallet, exchange and trading operations.
- Configuration and administrative changes.
- Secret access and network destinations.

Consider Open Policy Agent (OPA), Cedar or a small well-tested policy module if it fits the current architecture. Do not add a policy engine merely for fashion; centralize and test authorization decisions.

# 24. A2A AND MCP SECURITY HARDENING

A2A and MCP are separate protocol surfaces and must have separate identity, authorization and threat models. A2A communicates with external agents; MCP exposes tools/resources to model clients. Neither protocol makes a peer trustworthy.

## 24.1 A2A trust model

- External agents remain untrusted guests even after protocol authentication.
- Agent Cards describe claimed capabilities; they do not prove identity, safety, quality or organizational affiliation.
- Verify endpoint ownership/identity through a configured trust process, authenticated transport, signed credentials or an approved registration flow as supported.
- Use short-lived, audience-bound, scope-limited credentials; avoid shared global bearer tokens.
- Validate every task/message/artifact against protocol and internal schemas.
- Apply endpoint allowlists, SSRF controls, timeouts, response-size limits, concurrency limits, per-agent quotas and per-session budgets.
- Bind every task to a session ID, guest ID, correlation ID, expiry and permitted purpose.
- Reject replayed, expired, out-of-scope and late responses.
- Treat task status, cancellation and completion claims from the remote agent as untrusted until verified locally.
- Do not let external agents discover arbitrary internal tools or infer internal system topology.
- Never expose internal prompts, chain-of-thought, private memory, user secrets, provider credentials or unrestricted context.

## 24.2 A2A message quarantine

Normalize guest contributions into a bounded schema such as:
- Guest identity and verification state.
- Task/session/correlation IDs.
- Declared capability and requested task.
- Plain-language contribution.
- Structured claims and confidence.
- Evidence references and source timestamps.
- Proposed follow-up questions (not executable commands).
- Artifact references subject to scanning.
- Token/size/time accounting.

Do not accept executable code, shell commands, tool-call directives or claimed policy changes as executable instructions. A guest may recommend that a native agent check a public source; the native agent must independently decide and request the capability through the internal broker.

## 24.3 MCP server/tool security

If MCP is used:
- Register only explicitly approved MCP servers.
- Authenticate each server/client and use scoped permissions.
- Validate tool schemas and returned content.
- Apply the same broker, sandbox, egress, logging and cost controls as native adapters.
- Treat MCP resource contents and tool results as untrusted.
- Do not expose privileged write tools to general research agents.
- Separate read-only research MCP servers from administrative, wallet or execution servers.
- Require explicit user approval for consequential operations.
- Pin/verify server versions and review dependencies before enabling.
- Disable unknown or newly added tools until reviewed.

## 24.4 Trading and signing boundary

Makto may analyze, propose and paper-trade within its configured scope. Real transactions must be a separate high-risk capability:
- No external guest can invoke it.
- No research agent can directly invoke a signer.
- A trade proposal is not an execution authorization.
- Enforce user confirmation, transaction preview, chain/asset/recipient/amount/slippage/fee checks and policy limits.
- Use wallet-native signing or a dedicated signer with hardware/MPC controls where appropriate; never expose seed phrases/private keys to LLMs.
- Require simulation/preflight where supported.
- Record the exact user approval and signed transaction reference.
- Provide revocation, spending limits and emergency disable controls.

# 25. COST, LICENSING AND MAINTENANCE GOVERNANCE

The platform should be capable of using free, open-source, paid, premium and enterprise providers. It must not assume free is always best or expensive is always better.

## 25.1 Budget-aware execution

Implement configurable budgets at provider, capability, agent, session and global levels:
- Request count and rate limits.
- LLM input/output token budgets.
- Per-session and monthly cost ceilings.
- Compute/runtime ceilings for sandboxes.
- Browser and search request ceilings.
- A2A guest token/turn/time budgets.
- Data retention/storage limits where appropriate.

Support policy modes such as:
- **Cost-conscious:** prefer reliable free/public or lower-cost sources; use premium only when explicitly enabled or justified.
- **Balanced:** optimize quality, freshness, reliability and cost.
- **Quality-first:** allow premium sources/models within configured spending and licensing limits.
- **Manual-only:** require operator approval before activating a paid provider or exceeding a configured threshold.

These are configurable operating modes, not separate hardcoded agent personalities.

## 25.2 Cost-aware provider selection

Before each paid request, estimate cost where possible and check budget. If pricing is unknown, flag it and follow the configured policy. Do not repeatedly call expensive providers as automatic fallbacks without budget checks.

Use caching, shared retrieval, request coalescing, incremental updates and event-driven refresh. Cache TTL must depend on data type and task urgency; do not serve stale data as fresh. Avoid six agents independently fetching identical data.

## 25.3 Licensing and terms

Before integration, document:
- API/data terms and commercial use.
- Storage and retention permissions.
- Redistribution/display rights.
- Attribution requirements.
- Real-time/delayed data restrictions.
- User/region eligibility.
- Rate and quota limits.
- Whether a key is needed and where it is stored.
- Vendor lock-in and exit strategy.

Do not scrape or redistribute data in violation of provider terms. Do not assume a public endpoint permits commercial use.

## 25.4 No mandatory vendor lock-in

Use provider adapters and capability contracts. Keep vendor-specific response parsing inside adapters. Provide a documented way to disable, replace or remove a provider without changing agent prompts or core orchestration.

The architecture should remain useful if a provider changes pricing, removes a free tier, suffers an outage or discontinues an API.

# 27. IMPLEMENTATION PRIORITY AND DELIVERY RULE

Do not try to integrate the entire catalogue in one release. Implement the registry, capability contracts, security boundary, cost governance and a small set of verified high-value adapters first. Then add providers in task-driven phases.

The coding agent must:
1. Audit existing adapters and avoid duplicating them.
2. Build the shared registry and broker before exposing more tools to agents.
3. Add provider adapters based on actual task coverage and user configuration.
4. Include optional premium providers in the architecture and provider catalogue without requiring subscriptions or credentials.
5. Implement security and A2A boundaries before enabling external tool execution or guest access.
6. Use deterministic fixtures for tests and clearly label live verification blockers.
7. Keep the codebase maintainable; do not create a microservice for every adapter or a new framework for every capability.
8. Update architecture, provider, security, A2A, operations and test documentation.
9. Include a table of each candidate provider with capability, implementation state, access requirement, cost class (free/open-source, free-tier, paid, enterprise, unknown), license/terms verification status and reason for selection or deferral.
10. Explain which integrations were deliberately deferred and why.

**The goal is not to make ClawIntel call the most tools. The goal is to give ClawIntel access to the right tools, protect the system from untrusted inputs, and select the best available evidence for each task—without vendor lock-in, uncontrolled cost or unnecessary maintenance.**
